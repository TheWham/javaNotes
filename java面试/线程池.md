# Java 线程池复习笔记

## 1. 为什么要使用线程池？

线程池的核心作用是：

```text
复用线程
控制并发数量
管理任务队列
降低线程创建和销毁成本
防止系统被大量线程打爆
```

如果每来一个任务就创建一个线程：

```java
new Thread(() -> {
    // 执行业务
}).start();
```

高并发下会有几个问题：

```text
1. 线程创建和销毁成本高
2. 线程数量不可控
3. CPU 上下文切换严重
4. 内存消耗增加
5. 极端情况下 OOM
```

线程池就是为了解决这些问题。

---

## 2. ThreadPoolExecutor 七大核心参数

标准线程池创建方式：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        corePoolSize,
        maximumPoolSize,
        keepAliveTime,
        unit,
        workQueue,
        threadFactory,
        handler
);
```

### 2.1 corePoolSize：核心线程数

核心线程数表示线程池中长期保留的线程数量。

```text
即使线程空闲，默认也不会被销毁
```

例如：

```java
corePoolSize = 10
```

表示线程池至少维持 10 个核心线程。

---

### 2.2 maximumPoolSize：最大线程数

最大线程数表示线程池最多能创建多少个线程。

```java
maximumPoolSize = 20
```

表示线程池最多允许 20 个线程同时执行任务。

注意：

```text
是否会创建非核心线程，取决于队列是否满
```

---

### 2.3 keepAliveTime：非核心线程存活时间

当线程数超过核心线程数时，多出来的非核心线程如果空闲超过这个时间，就会被销毁。

例如：

```java
60L, TimeUnit.SECONDS
```

表示非核心线程空闲 60 秒后销毁。

如果：

```java
corePoolSize == maximumPoolSize
```

那么 `keepAliveTime` 基本没有意义，因为没有非核心线程。

除非调用：

```java
executor.allowCoreThreadTimeOut(true);
```

让核心线程也允许超时销毁。

---

### 2.4 unit：时间单位

用于配合 `keepAliveTime`。

常见：

```java
TimeUnit.SECONDS
TimeUnit.MILLISECONDS
TimeUnit.MINUTES
```

---

### 2.5 workQueue：任务队列

当核心线程都在忙时，新任务会先进入任务队列。

常见队列：

```text
ArrayBlockingQueue：有界队列
LinkedBlockingQueue：默认可无界，也可以指定容量
SynchronousQueue：不存任务，直接交给线程执行
PriorityBlockingQueue：优先级队列
DelayedWorkQueue：延迟任务队列
```

生产中更推荐使用：

```java
new ArrayBlockingQueue<>(500)
```

或者：

```java
new LinkedBlockingQueue<>(500)
```

重点是：

```text
队列要有界
```

否则任务无限堆积，可能 OOM。

---

### 2.6 threadFactory：线程工厂

用于自定义线程名称、是否守护线程、异常处理等。

不推荐直接用默认线程名，因为排查问题不方便。

推荐写法：

```java
new ThreadFactory() {
    private final AtomicInteger count = new AtomicInteger(1);

    @Override
    public Thread newThread(Runnable r) {
        Thread thread = new Thread(r);
        thread.setName("cache-rebuild-" + count.getAndIncrement());
        thread.setDaemon(true);
        return thread;
    }
}
```

好处：

```text
1. 日志中能看出线程属于哪个业务
2. 排查线程池问题更方便
3. 便于监控和定位
```

---

### 2.7 handler：拒绝策略

当线程池线程数达到最大值，并且队列也满了，新任务会触发拒绝策略。

常见拒绝策略：

```text
AbortPolicy：抛出异常，默认策略
DiscardPolicy：直接丢弃任务，不抛异常
DiscardOldestPolicy：丢弃队列中最老的任务
CallerRunsPolicy：由提交任务的线程自己执行任务
```

---

## 3. 线程池执行流程

假设线程池参数是：

```java
corePoolSize = 10
maximumPoolSize = 20
queueCapacity = 500
```

任务提交后的执行流程：

```text
1. 当前线程数 < corePoolSize
   => 创建核心线程执行任务

2. 当前线程数 >= corePoolSize，且队列没满
   => 任务进入队列等待

3. 队列满了，且当前线程数 < maximumPoolSize
   => 创建非核心线程执行任务

4. 队列满了，且当前线程数 >= maximumPoolSize
   => 执行拒绝策略
```

重点：

```text
线程池不是先扩容到 maximumPoolSize，再放队列
而是核心线程满了之后，先放队列
队列满了之后，才创建非核心线程
```

## 4. Executors 常见线程池

### 4.1 newFixedThreadPool

```java
Executors.newFixedThreadPool(10);
```

特点：

```text
核心线程数 = 最大线程数
线程数量固定
使用无界 LinkedBlockingQueue
```

适合：

```text
任务数量可控
后台批处理
固定并发度任务
```

不适合：

```text
高并发 Web 请求触发的异步任务
任务来源不可控的场景
```

风险：

```text
无界队列可能导致任务堆积，最终 OOM
```

一句话：

```text
固定线程数处理任务，但无界队列有风险
```

---

### 4.2 newCachedThreadPool

```java
Executors.newCachedThreadPool();
```

特点：

```text
核心线程数 = 0
最大线程数 = Integer.MAX_VALUE
使用 SynchronousQueue
空闲线程 60 秒后销毁
```

适合：

```text
大量短小任务
任务执行很快
并发量可控
```

不适合：

```text
高并发慢任务
IO 阻塞严重的任务
```

风险：

```text
可能创建大量线程，导致线程爆炸或 OOM
```

一句话：

```text
来任务就尽量创建线程执行，适合短任务，不适合高并发慢任务
```

---

### 4.3 newSingleThreadExecutor

```java
Executors.newSingleThreadExecutor();
```

特点：

```text
只有一个线程
任务按提交顺序串行执行
使用无界 LinkedBlockingQueue
```

适合：

```text
有顺序要求的任务
单线程消费任务
串行化处理
```

不适合：

```text
任务量大
任务耗时长
不能接受排队延迟的场景
```

风险：

```text
队列无界，任务堆积可能 OOM
```

一句话：

```text
保证任务串行执行，但吞吐低，队列有堆积风险
```

---

### 4.4 newScheduledThreadPool

```java
Executors.newScheduledThreadPool(5);
```

特点：

```text
支持延迟执行
支持周期执行
使用延迟任务队列
```

常见方法：

```java
executor.schedule(task, 3, TimeUnit.SECONDS);
executor.scheduleAtFixedRate(task, 1, 5, TimeUnit.SECONDS);
executor.scheduleWithFixedDelay(task, 1, 5, TimeUnit.SECONDS);
```

适合：

```text
定时刷新缓存
定时清理任务
周期性心跳
延迟任务
```

不适合：

```text
强可靠分布式调度任务
```

因为本地定时任务依赖当前 JVM，服务宕机后任务就没了。

一句话：

```text
适合单机延迟任务和周期任务，不适合强可靠分布式调度
```

---

### 4.5 newSingleThreadScheduledExecutor

```java
Executors.newSingleThreadScheduledExecutor();
```

特点：

```text
单线程
支持延迟和周期任务
任务串行执行
```

适合：

```text
简单定时任务
定时打印统计日志
定时清理本地缓存
```

不适合：

```text
多个耗时定时任务
任务之间不能互相阻塞的场景
```

风险：

```text
一个任务卡住，后面的任务都会被影响
```

一句话：

```text
单线程定时任务，简单但容易被慢任务阻塞
```

---

### 4.6 newWorkStealingPool

```java
Executors.newWorkStealingPool();
```

特点：

```text
底层是 ForkJoinPool
使用工作窃取算法
默认并行度接近 CPU 核心数
```

工作窃取的意思是：

```text
每个线程有自己的任务队列
某个线程任务执行完后，可以去其他线程队列中偷任务执行
```

适合：

```text
CPU 密集型任务
递归分治任务
并行计算任务
```

例如：

```text
大数组并行计算
递归拆分任务
批量数据聚合
```

不适合：

```text
IO 阻塞任务
数据库查询
HTTP 调用
Redis 调用
```

一句话：

```text
适合 CPU 密集型分治计算，不适合 IO 阻塞任务
```

## 5. 为什么不推荐直接使用 Executors？

阿里 Java 开发规范中不推荐直接使用 `Executors` 创建线程池。

原因是很多默认参数不可控。

例如：

```java
Executors.newFixedThreadPool(10);
```

底层使用无界队列：

```java
new LinkedBlockingQueue<>()
```

如果任务大量堆积，可能 OOM。

再比如：

```java
Executors.newCachedThreadPool();
```

最大线程数是：

```java
Integer.MAX_VALUE
```

如果请求暴涨，可能创建大量线程，导致 OOM。

所以生产环境更推荐直接使用：

```java
new ThreadPoolExecutor(...)
```

显式指定：

```text
核心线程数
最大线程数
队列容量
线程工厂
拒绝策略
```

## 6. 常见拒绝策略详解

### 6.1 AbortPolicy

默认策略。

```java
new ThreadPoolExecutor.AbortPolicy()
```

行为：

```text
直接抛出 RejectedExecutionException
```

适合：

```text
任务不能丢
需要让调用方感知失败
```

缺点：

```text
可能影响主流程
```

---

### 6.2 DiscardPolicy

```java
new ThreadPoolExecutor.DiscardPolicy()
```

行为：

```text
直接丢弃新任务
不抛异常
不打印日志
```

适合：

```text
可丢弃任务
非核心异步任务
缓存重建任务
监控上报任务
```

缺点：

```text
静默丢弃，不方便排查
```

更推荐自定义日志版丢弃策略。

---

### 6.3 DiscardOldestPolicy

```java
new ThreadPoolExecutor.DiscardOldestPolicy()
```

行为：

```text
丢弃队列中最老的任务
然后尝试提交当前任务
```

适合：

```text
只关心最新任务的场景
```

例如：

```text
实时刷新任务
状态更新任务
```

不适合：

```text
每个任务都必须执行的场景
```

---

### 6.4 CallerRunsPolicy

```java
new ThreadPoolExecutor.CallerRunsPolicy()
```

行为：

```text
由提交任务的线程自己执行任务
```

适合：

```text
任务不能丢
同时希望反向限制提交速度
```

例如 Web 请求线程提交任务，线程池满了，当前请求线程自己执行任务。

优点：

```text
不会丢任务
可以形成反压
```

缺点：

```text
可能拖慢调用方
影响接口响应时间
```

## 7. 项目中的缓存重建线程池设计

你的缓存逻辑是：

```text
缓存逻辑过期
    ↓
当前请求返回旧数据
    ↓
异步线程重建缓存
```

这个场景的特点是：

```text
1. 重建任务不是强一致任务
2. 不是每个请求都必须提交任务
3. 只要有一个线程完成重建即可
4. 当前请求可以返回旧数据
5. 高并发下要防止任务堆积
```

所以不适合直接使用：

```java
Executors.newFixedThreadPool(10);
```

因为它底层是无界队列。

---

## 8. 推荐的缓存重建线程池

```java
private static final ExecutorService CACHE_REBUILD_EXECUTOR =
        new ThreadPoolExecutor(
                10,
                10,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(500),
                new ThreadFactory() {
                    private final AtomicInteger count = new AtomicInteger(1);

                    @Override
                    public Thread newThread(Runnable r) {
                        Thread thread = new Thread(r);
                        thread.setName("cache-rebuild-" + count.getAndIncrement());
                        thread.setDaemon(true);
                        return thread;
                    }
                },
                (r, executor) -> {
                    log.warn("缓存重建任务被拒绝，activeCount={}, queueSize={}",
                            executor.getActiveCount(),
                            executor.getQueue().size());
                }
        );
```

参数解释：

```text
核心线程数 10：
最多 10 个核心线程处理缓存重建

最大线程数 10：
固定 10 个线程，不额外扩容

队列容量 500：
最多积压 500 个重建任务，防止无限堆积

自定义线程名：
方便日志排查

拒绝策略：
线程池满了后记录日志，丢弃任务
```

为什么可以丢弃？

因为逻辑过期场景下：

```text
当前请求会返回旧数据
缓存重建任务不是每个都必须执行
只要后续有一个任务成功重建即可
```

## 9. 缓存重建任务提交前最好加锁

即使使用有界线程池，也不应该让所有请求都提交重建任务。

错误做法：

```text
10000 个请求发现缓存过期
10000 个请求都 submit 重建任务
```

正确做法：

```text
先抢重建锁
抢到锁的线程才提交异步任务
没抢到锁的线程直接返回旧数据
```

推荐使用 Redis `SET NX EX` 作为重建标记：

```java
Boolean locked = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);

if (Boolean.TRUE.equals(locked)) {
    CACHE_REBUILD_EXECUTOR.execute(() -> {
        try {
            // double check
            RedisData<R> currentData = getRedisData(cacheKey, type);
            if (currentData != null &&
                    currentData.getExpireTime() > System.currentTimeMillis()) {
                return;
            }

            R dbResult = dbFallback.apply(bloomValue);
            if (dbResult != null) {
                setWithLogicalExpire(cacheKey, dbResult, logicalExpireMs);
            }
        } finally {
            stringRedisTemplate.delete(lockKey);
        }
    });
}

return redisData.getData();
```

这样可以保证：

```text
同一个缓存 key 同一时间只有一个重建任务被提交
```

## 10. 线程池参数怎么设置？

没有固定答案，要根据任务类型决定。

### 10.1 CPU 密集型任务

比如：

```text
加密解密
复杂计算
图片处理
数据压缩
```

线程数建议：

```text
CPU 核心数 + 1
```

原因：

```text
CPU 密集型任务主要消耗 CPU
线程太多会增加上下文切换
```

---

### 10.2 IO 密集型任务

比如：

```text
数据库查询
Redis 调用
HTTP 调用
文件读写
```

线程数可以比 CPU 核心数更大。

常见估算：

```text
线程数 = CPU 核心数 * 2
```

或者根据压测结果调整。

因为 IO 任务大部分时间在等待，适当增加线程数可以提高吞吐。

---

### 10.3 缓存重建任务

缓存重建一般是：

```text
查数据库 + 写 Redis
```

属于 IO 密集型任务。

但它是保护系统的异步任务，不能无限扩大线程数。

所以建议：

```text
线程数不宜太大
队列必须有界
任务可以丢弃
提交前最好加锁
```

例如：

```text
核心线程数：5~10
最大线程数：10~20
队列容量：100~1000
拒绝策略：记录日志后丢弃
```

具体要根据数据库承载能力和压测结果调整。

## 11. 你的项目面试回答

可以这样回答：

```text
在逻辑过期缓存方案中，我使用线程池异步重建热点缓存。初版使用的是 newFixedThreadPool，但我后面意识到它底层是无界队列，在热点 key 过期并发量很高时，大量请求可能同时提交重建任务，导致任务堆积甚至 OOM。

所以我改成了自定义 ThreadPoolExecutor，设置固定 10 个重建线程，并使用 ArrayBlockingQueue 限制队列容量为 500，避免任务无限堆积。同时自定义线程名，方便日志排查；拒绝策略选择记录日志后丢弃，因为逻辑过期场景下当前请求会返回旧数据，缓存重建任务不是每个都必须执行。

另外，我会在提交任务前通过 Redis SET NX EX 或分布式锁控制同一个缓存 key 只有一个线程提交重建任务，避免大量无效任务进入线程池。
```

## 12. 高频面试题

### 问题 1：为什么不建议使用 Executors？

回答：

因为 `Executors` 创建的线程池很多默认参数不可控。比如 `newFixedThreadPool` 和 `newSingleThreadExecutor` 使用无界队列，任务过多可能导致 OOM；`newCachedThreadPool` 最大线程数是 `Integer.MAX_VALUE`，高并发下可能创建大量线程，也可能 OOM。所以生产环境更推荐直接使用 `ThreadPoolExecutor`，显式指定核心线程数、最大线程数、队列容量、线程工厂和拒绝策略。

---

### 问题 2：线程池的执行流程是什么？

回答：

线程池收到任务后，先判断核心线程是否已满。如果核心线程没满，就创建核心线程执行任务；如果核心线程已满，就把任务放入队列；如果队列也满了，并且当前线程数小于最大线程数，就创建非核心线程执行任务；如果线程数已经达到最大线程数，并且队列也满了，就执行拒绝策略。

---

### 问题 3：核心线程数和最大线程数有什么区别？

回答：

核心线程数是线程池长期保留的线程数量，默认情况下即使空闲也不会销毁。最大线程数是线程池允许创建的最大线程数量，只有在核心线程都忙并且任务队列满了之后，才会创建非核心线程，直到达到最大线程数。

---

### 问题 4：为什么你的缓存重建线程池要用有界队列？

回答：

因为逻辑过期缓存遇到热点 key 过期时，可能有大量请求同时触发异步重建。如果使用无界队列，任务会无限堆积，可能导致内存压力甚至 OOM。使用有界队列可以限制最大积压任务数，超过容量后执行拒绝策略，保护系统稳定性。

---

### 问题 5：缓存重建任务为什么可以丢弃？

回答：

因为逻辑过期方案下，当前请求会直接返回旧数据，异步重建只是为了刷新缓存，不是当前请求成功的必要条件。对于同一个热点 key，只需要有一个任务成功重建即可，并不是每个请求提交的任务都必须执行。所以线程池满时，可以丢弃部分重建任务，避免异步任务反过来拖垮系统。

---

## 13. 一句话总结

线程池的核心是控制并发和任务积压。生产环境不推荐直接使用 `Executors`，而应该使用 `ThreadPoolExecutor` 显式设置线程数、有界队列、线程工厂和拒绝策略。对于逻辑过期缓存重建场景，线程池必须有界，任务允许丢弃，并且最好在提交任务前通过锁控制同一个 key 只提交一个重建任务。
